# Weekly Planner —— 软件说明

> 这份文档是写给「没看过代码、也没用过这个 app 的人」的，包括 AI。
> 读完应该能回答：这是什么、为什么这么做、已经有什么、还缺什么。

---

## 1. 一句话

一个给自己一个人用的**周计划 + 日程 + 打卡** web app，
最核心的一点是：**计划（Plan）和实际（Actually）在时间轴上并排画出来**。

不是团队协作工具，不是任务管理系统，也没有 AI 自动排程。
它要替代的东西是**纸质 weekly planner**。

---

## 2. 从哪来的

作者原本用纸质 planner，也有一个自己写的日记 app。
这个 planner 和日记是**两个独立的项目**（各自的 repo、各自的 Vercel 项目），
但**共用同一个 Supabase 实例和同一套 `auth.users`**：
同一个 Google 账号登录，两边是同一个 `user_id`，各自的表靠 RLS 隔离。

第一版的目标明确排除了 AI 排程 —— 「不用 AI，我自己排，软件负责算清楚和画清楚」。

---

## 3. 技术栈

| | |
|---|---|
| 前端 | React 19 + Vite 8，无 UI 框架，手写 CSS |
| 状态 | 一个 `usePlanner` hook，没有 Redux/Zustand |
| 后端 | Supabase（Postgres + RLS + Google OAuth / Magic Link） |
| 部署 | Vercel |
| 打包 | 手写 service worker + 构建期生成 precache manifest 的 Vite 插件（PWA） |
| 检查 | oxlint。没有单元测试框架，验证靠 Playwright 脚本（不在项目依赖里） |
| 其它 | date-fns。没有 UI 组件库、没有拖拽库、没有日历库 |

数据层是 **repo 模式**：`repo/mock.js`（localStorage）和 `repo/supabase.js`
接口完全一致，没配 `.env.local` 时自动走 mock，UI 层感知不到差别。
这让「不连数据库调 UI」和「自动化测试」都很便宜。

## 4. 数据模型

五张表，都带 `user_id` + RLS。

### `templates` —— 每周重复的事

```
id, user_id, title, type, priority, recurrence, recurrence_days[],
start_time, end_time, min_duration_minutes, max_duration_minutes,
color, keep_in_todo, is_active, created_at
```

- `type`：`event`（有起止时间，上时间轴）/ `todo`（只有事没有时间）/ `habit`（每天重复、按完成度打卡）
- `recurrence`：`weekly`（选星期几）或 `monthly`（每月某一天，比如交房租）

### `schedule_entries` —— 某一天的一条具体安排

```
id, user_id, template_id, date, title,
planned_start, planned_end, actual_start, actual_end,
status, rescheduled_from, completion_pct, note,
min_duration_minutes, max_duration_minutes, color, keep_in_todo, created_at
```

- `status`：`planned` / `in_progress` / `done` / `skipped` / `rescheduled`
- **计划和实际是四个独立的字段**，不是一组时间加一个「是否完成」。
  这是整个 app 的地基。
- `(template_id, date)` 唯一 —— 重复生成时靠它幂等。

### 另外三张

- `habits_log`：`(template_id, date, completion_pct, note)`
- `weekly_focus`：一周最多 3 条本周重点
- `special_days`：某一天的标签（「专注学习」这种）

## 5. 界面：两个视图，三个模块

### 模块顺序固定：**To do → Time schedule → Habits**

周视图和日视图都是这个顺序。早期版本把三者混在一起（靠「时长短于 20 分钟
算待办」这种启发式分流），结果没填时间的固定事件掉进待办、习惯该出现的地方
不出现。现在用 `type` 显式区分。

### 周视图

- To do 和 Habits 是 **n×8 的表格**（左边 n 个项目，右边周一到周日）。
  点格子在 **100 / 50 / 0** 之间循环。
  待办没打分算 0（红）—— 一眼看出任务落在哪天还没做；
  习惯没打卡留空白 —— 默认全红太吓人。
- 中间是 **7 条并排的时间轴**，一眼看这周排得满不满。
- 点日期进日视图。窄屏上时间块缩成色条只看分布。

### 日视图

- **完整 24 小时一次画完**（每小时 44px，共 1056px），
  卡片里**不再套滚动** —— 嵌套滚动在手机上是灾难。睡眠也画得下。
- 时间轴是两栏：左 **Plan**，右 **Actually**，中间是刻度。
  两栏各铺一层很淡的底色（左偏橙、右偏绿）。

## 6. 核心设计决定（这部分才是重点）

### 6.1 Plan / Actually 并排

这是这个 app 和其它日程工具最大的差别。绝大多数工具只有一条时间轴，
「完成」是一个复选框。这里两栏并排，你能直接看出：
计划 9:30 上班实际 9:40 到、计划 21:00 读书实际下午三点读的。

配套的一整套操作：

- 双击左边的块 = 完成，实际时间自动照抄计划（最常见的情况，一下搞定）
- 双击右边的块 = 撤销完成
- 待办上点「▶ 开始」= 计时，右边的块跟着长到「现在」，「■ 结束」落定
- 长按右边的块 → 编辑器把**实际**那组时间放最上面 → 点「开始/结束」那格
  浮出「现在 19:42 · OK」

### 6.2 占用时段：做完的按实际算，没做的按计划算

「今天还空着多少」和「排入放哪」都要知道哪些时段被占了。
**不能一刀切成按实际算 —— 未来根本没有实际。** 规则按状态分：

| 条目 | 占哪一段 |
|---|---|
| 做完了（有实际起止） | **实际**那一段，计划那段就此让出来 |
| 正在做 | 实际开始 → max(现在, 计划结束) |
| 跳过了 | 不占 |
| 还没做、有计划 | **计划**那一段 |

效果最直观的是提前做完：计划 21:00 读书、下午三点读完了，
那 21:00–22:00 现在真的是空的，加减法会多算这一小时，「排入」也会放进去。

「算空闲」和「找空档」共用同一份占用时段 —— 不然会出现
「说还剩两小时、一点排入却塞不进去」这种自相矛盾。

### 6.3 弹性任务：时长是个区间

「购物 30–60 分钟」「晚餐 1 小时」—— 知道要多久，不知道几点开始。
这类事在纸上最难安排，在大多数 app 里也没有位置（要么是固定日程，
要么是没有时长的待办）。

- 待办可以写 `min_duration_minutes` / `max_duration_minutes`
- 点「排入 →」自动找当天第一个装得下的空档（按上限算），
  再排下一个自然接在后面 —— 「下班后购物、晚餐、洗澡」点三下依次排好
- **装不下也照排**（接在最后一个块后面，哪怕过了 24 点），只是标红。
  拒绝排入只会逼人跑去别处手动填时间；排上去、标红、自己拖，更有用。

### 6.4 块画成什么样，全部是算出来的

没有「是否已敲定」这类字段：

| 样子 | 什么时候 |
|---|---|
| 实心 | 起止都定死（min = max）且不和别的块冲突 |
| 半透明 | 时长还是个区间，没定死 |
| 红色 | 和别的块撞了 |

**少一个字段就少一处可能和现实对不上的状态。** 同样的原则用在颜色上：
颜色不往条目上复制（复制过就成了快照，改模板不会回头更新已生成的条目），
而是渲染时从模板解析；条目自己填了颜色才算「单独改过这一条」。

### 6.5 手势与触摸

- 拖动用 **Pointer Events**，不用 HTML5 drag-and-drop（后者在触摸屏上根本不触发）
- 块上只有**左边一道竖条**（挪时间）和**底边一道横条**（改时长）是拖动区，
  只有这两条设 `touch-action: none`。整块都能拖的话，手指落在块上就滚不动
  1056px 高的时间轴了
- **长按块** = 打开编辑，并且**从哪一栏长按，编辑器就把哪一组时间放最上面**
- **长按空白处** = 在那个时间加一条（挑一件今天还没安排的，或直接写新的）。
  不做成单击：手机上滚页面时手指落在时间轴上是常事，单击会一路误开。
  长按 520ms 才认，手一动超过 8px 就取消；不碰 `touch-action`、不 `preventDefault`，
  空白处必须能照常滚页面
- 拖动可以**多选一起拖**；开着「顺延」时拖一个块，它之后的块跟着挪同样的量
  （一件事提前或延误，后面自动跟上）。顺延**只对 Plan 生效** ——
  Actually 是已经发生的事，不该被顺手改掉

### 6.6 时间输入

不用 `<input type="time">`（手机上点转盘太慢）。

- **开始 / 结束 / 时长填两个，第三个自动算**
- 写法宽松：`9` / `930` / `0930` / `9:30`；时长 `90` / `1:30` / `1.5h` / `45m`
- 输入框里存的是**原文**，只在失焦时规范成 `09:30` ——
  不然打「930」在打完「9」的瞬间就被改写成「09:00」，光标还跟着跳
- 编辑时旁边有一条当天的缩略时间轴，能看到哪些时段是空的

### 6.7 撤销

**对所有操作有效**，右下角固定一个图标按钮（以前放顶栏，页面一长就找不到）。

实现上不存整份状态快照，而是**每个操作记录自己的逆操作**：
改一条就记改之前的那几个字段，删一条就记整行（连 id 一起还原）。
一次拖动改了好几个块算**一步**。栈深 30，刷新后清空。

### 6.8 配色

莫兰迪（低饱和、掺灰），主色是陶土橙。七个事项颜色**是算出来的不是挑出来的**：
上一版八个颜色两两之间的 CIEDE2000 感知差异最小只有 3.3（基本分不出），
原因是色相全挤在一起、块底又是接近白的淡色。
重做后色相均匀铺开、删掉一个孪生色、明度也拉开，最小 ΔE 从 3.3 提到 10.4，
块底压深色标题的对比度 ≥ 7.3。彩度上限卡在 17，保住掺灰的调子 ——
放开彩度能把 ΔE 拉到 12 以上，但那就成糖果色了。

## 7. 已经有的功能（清单）

- 模板（每周 / 每月重复）→ 一键补齐这一周的安排
- 三个模块：To do / Time schedule（24h 双栏）/ Habits
- 待办：完成度 100/50/0、备注、时长区间、一键排入、排入后可选保留在列表
- 时间轴：拖动挪时间、拖底边改时长、多选一起拖、顺延、撞车标红
- 计划 ↔ 实际：双击完成、计时器（开始/结束）、「现在」一键填、只记实际
- 空白处长按快捷加一条（两栏都支持）
- 「装不装得下」加减法（按实际 + 计划混合计算）
- 习惯打卡（周视图 n×8 表格）
- 本周重点（最多 3 条）、特殊日标签
- 事项配色（模板级 + 单条覆盖）
- 全局撤销（含 Ctrl/⌘+Z）
- PWA：可装到手机桌面，界面离线可打开
- 帮助页（手势和功能说明）
- Google 登录 / Magic Link
- 本地 mock 模式（不连数据库也能跑）

## 8. 还没有的东西（诚实清单）

**功能上：**

- **没有提醒 / 通知**。对一个 planner 来说这是最大的缺口。
- **不和系统日历或 Google Calendar 同步**。日程还得手动录一遍。
- **没有统计 / 回顾**。数据模型留了位置（计划 vs 实际的差值本来就存着），
  但界面还没做。原始计划是保留 4 周明细 + 长期只留统计量。
- 没有搜索、没有项目/标签层级、没有优先级排序视图。
- 没有周计划到日计划的自动拆解。
- 没有附件、没有子任务。

**工程上：**

- **离线只读**。service worker 缓存了界面资源，但写操作要联网，没有离线队列。
- **多设备不实时同步**，要刷新页面。
- **撤销不跨刷新**（栈在内存里）。
- **视图状态不进 URL** —— 刷新回到周视图，安卓返回手势直接退出 app。
- **没有自动化测试套件**。验证靠临时写的 Playwright 脚本，不在 CI 里。
- **时区**：`date` 是本地日期字符串，时间戳是 `timestamptz`。跨时区旅行时
  这两者的关系没有专门处理过。
- 单用户。没有协作、没有分享。

## 9. 和市面上产品的关系

不是要做一个产品，是要做一个**比纸质 planner 好用的私人工具**。
所以取舍和商业产品不一样：

- **不做 AI 自动排程**（Motion / Reclaim 那一类的核心卖点）。
  作者明确要自己排，软件只负责算清楚和画清楚。
- **不做协作**，所以没有权限、通知、评论这些东西。
- 把力气花在**「计划 vs 实际」的可视化**和**「不确定时长的事怎么安排」**上 ——
  这两件事恰好是通用日历和通用待办工具都不太管的。

反过来说，凡是一个商业 planner 靠**集成**取胜的地方（日历同步、提醒、
跨设备实时同步、统计报表），这个 app 目前都是空的。

## 11. 如果要给建议，作者最想听的是

1. **提醒和日历同步**这两个缺口，哪个更值得先做，怎么做代价最小。
2. **统计 / 回顾**该看什么。手里有「计划 vs 实际」的完整历史，
   这是大多数工具没有的数据，但不知道拿它看什么才真的有用。
3. 「计划 vs 实际」这个模型有没有被现成的产品或研究做过，
   有没有值得借鉴的交互。
4. 现在的手势（长按块 / 长按空白 / 拖两道窄条 / 双击）是不是太多了，
   有没有更少的一套能覆盖同样的操作。

# Weekly Planner

个人日程规划 App —— 在「喜欢做的事」和「该做但容易忽视的事」之间找平衡。

当前进度：**Step 1**（手动排程 + 打卡 + 复用模板，不做 AI 排程）。

## 跑起来

```bash
npm install
npm run dev
```

**不配 Supabase 也能直接跑。** 没有 `.env.local` 时 App 自动进入「本地模式」：
数据存在浏览器 localStorage，还会灌一份示例模板，用来确认 UI 布局。

## 接 Supabase

和日记 App 是**两个独立的 project**（独立仓库、独立 Vercel Project），
只是共用同一个 Supabase 实例。所以：

- 建表 SQL 归本仓库管（`db/0001_init.sql`），**不要放进日记 App 的仓库或它的 migrations 目录**。
- 表名都是本项目自己的（`templates` / `schedule_entries` / `habits_log` /
  `weekly_focus` / `special_days`），不碰日记 App 的任何表。

步骤：

1. 打开 Supabase 控制台 → SQL Editor，按顺序跑 `db/` 下的脚本（都可重复执行）：
   - `0001_init.sql` — 建 5 张表并打开 RLS
   - `0002_entry_unique_constraint.sql` — 唯一约束修正（可选）
   - `0003_task_types.sql` — **必须跑**。类型从 `fixed_event/task/habit`
     改成 `event/todo/habit`，同时按「有没有填时间」修正存量数据。
     不跑的话新建模板会被数据库的 check 约束挡下来。
   - `0004_todo_progress.sql` — **必须跑**。给 `schedule_entries` 加
     `completion_pct` 和 `note`，待办才有完成度和备注。
   - `0005_flexible_blocks.sql` — **必须跑**。给 `schedule_entries` 加
     `min_duration_minutes` / `max_duration_minutes`，待办才有时长区间。
   - `0006_color_and_keep.sql` — **必须跑**。加 `color`（配色）和
     `keep_in_todo`（排进时间轴后仍留在待办）。
   - `0007_categories_and_rollup.sql` — **必须跑**。加 `categories`（分类）
     和 `daily_rollup`（每日汇总），统计的地基。
   - `0008_category_colors.sql` — 可选，只改数据。把已经建好的六个默认分类
     改成指定配色（新建的库不用跑，`DEFAULT_CATEGORIES` 里已经是这套了）。
     它会覆盖这六个分类当前的颜色，跑一次就够，之后在设置里改。
   - `0009_soft_delete.sql` — **必须跑**。加 `deleted_at`，删除改成打墓碑。
     不跑的话，在 Day View 里删掉的模板条目一刷新又会长回来。
2. 复制 `.env.local.example` 为 `.env.local`，填 URL 和 anon key。
3. 重启 `npm run dev`。这时会先要求登录。

### 登录 / Redirect URL（重要）

登录方式是 **Google 登录**，邮箱 magic link 作为兜底。Google provider 在共用的
Supabase 实例里已经开好了（日记 App 在用），本项目不用再配。

但有个坑：**Supabase 只接受白名单里的回跳地址**。不在白名单里的 `redirectTo`
会被静默忽略，直接退回 Site URL —— 而 Site URL 是日记 App 的地址，
所以登录链接会把你送到日记 App 去。

去 Supabase → Authentication → URL Configuration → **Redirect URLs**，
把本项目的地址都加进去（Site URL 保持日记 App 的不动）：

```
http://localhost:5173/**
https://<本项目的 Vercel 域名>/**
https://<本项目>-*.vercel.app/**    # 预览部署，可选
```

两个 App 共用同一份 `auth.users`，用同一个 Google 账号登录，两边就是同一个
`user_id`；各自的表靠 RLS 隔离，互相看不到对方的数据。

想在已经配好 `.env.local` 的情况下继续用假数据调 UI，
在 `.env.local` 里加一行 `VITE_USE_MOCK=1` 即可。

## 三个模块

界面就是三块，互不混淆，两个视图里顺序都一样：**To do → Time schedule → Habits**。

模板的 `type` 决定它归哪一块，不靠猜：

| type | 含义 | 出现在 |
|---|---|---|
| `event` | 有起止时间 | Time schedule（时间轴） |
| `todo` | 只有事，没有时间 | To do |
| `habit` | 只有事，没有时间，每天重复 | Habits |

> 早先的版本是按「时长短于 20 分钟就算待办」来分流的。结果是没填时间的固定事件
> 被判成待办、habit 该出现的地方不出现。类型自己说清楚是什么，就不用猜了。

- **Week View**：To do 的 n×8 表格 → 7 个并排时间轴 → Habits 的 n×8 表格。
  时间轴上**做完的画实际、没做的画计划**（见下）。
- **Day View**：当天待办表格 → 左 Plan / 中刻度 / 右 Actually → 当天打卡表格。
- **To do 和 Habits 用同一套组件**（`WeekProgressGrid` / `ProgressTable`），
  长得一样、操作一样，不用记两套。都是完成度 + 备注，点一格在 100 / 50 / 0 之间循环。
- 两者只有「还没打分时长什么样」不同：
  **待办按 0 显示成红色**（一眼看出任务落在哪天），**习惯留空白**（不然满屏红）。
- **7 列一定要放得下**：n×8 表格以前给自己留了 `min-width: 320px`、名字列
  `min-width: 5.5rem` 且 `nowrap`，390px 的手机上表格宽 339px、可视只有 329px，
  **周日被切掉 10px**，320px 上差 80px。一周的表格看不到周日，等于白做。
  现在改成 `table-layout: fixed`、名字列固定 `7rem`（<380px 收到 `4rem`），
  剩下的宽度七等分。代价是名字长了会截断 —— **点名字展开看全称**，
  只让那一行变高，列宽一格不动（量过：116/37/31/34/28 五种宽度下展开前后完全一致）。
  > 踩过的坑：`table-layout: fixed` 下 **`max-width` 对单元格无效**，
  > 列宽只认 `width`。第一版写的 `max-width: 5.5rem` 在 320px 上照样溢出 3px。
- **时间轴完整 24 小时**，卡片里不再套一层滚动 —— 套滚动会看不到全天，还老滚错层。
- 表格的行按「模板创建顺序 → 标题」稳定排序。之前跟着数据返回顺序走，
  数据一变行就跳位置，正要点的那行换到别处去了。
- 窄屏（手机）下：时间块缩成色条只看分布，点日期进 Day View 看内容。

## 时间输入

不用 `<input type="time">` 那个时钟控件，全部手打（手机上点转盘太慢）。

- **开始 / 结束 / 时长填两个，第三个自动算**（`src/lib/time.js` 的 `reconcile`）。
- 写法很宽松：`9` / `930` / `0930` / `9:30` 都认；时长可以写 `90` / `1:30` / `1.5h` / `45m`。
- 输入框里存的是原文，只在失焦时规范成 `09:30`。不然打「930」在打完「9」的
  瞬间就被改写成「09:00」，光标也跟着跳。
- 编辑时右边有一条当天的**缩略时间轴**，能看到哪些时段是空的、有没有撞车。
- **计划和实际是两组独立的输入**。之前只有一组，在 Actually 那栏点「改时间」，
  改的其实是计划。

### 别再填错那一组

分成两组之后还是会填错：两块长得一模一样，计划永远在上面，从 Actually 那栏
长按进来的人照着习惯往第一格里打。所以又补了三件事：

- **从哪一栏进来，那一组就排在最上面**，光标直接落在它的「开始」里。
- 两组各有底色：**计划偏橙、实际偏绿**，时间轴那两栏也铺同一层很淡的底。
  顺序会变，颜色不会 —— 真正让人一眼分清的是这个。
  （栏底色只铺在栏上，块自己的分类配色不动：颜色是用来认「这是什么事」的，
  不能被「这是哪一栏」抢走。）
- 右边那条缩略时间轴画的是正在改的那一组。改实际时不再报「撞车」：
  实际时间和别人的计划重叠不是错，你就是那个点做的。

### 编辑器要一屏放得下

日常的循环是「双击计划块完成 → 长按实际块把结束时间改成真的」，
一天要走十几遍。原先每一遍都要在弹窗里往下滑找保存键。

- **保存/取消钉在弹窗底部**（`position: sticky`）。弹窗本身就是滚动容器，
  所以 sticky 就够，不用把内容再包一层。负外边距抵消卡片内边距，
  让底栏铺满宽度 —— 不然内容会从两侧的缝里透出来。
- **不常用的字段收进「更多设置」**：时长区间 / 分类 / 颜色 / 「留在待办」/
  清空时间。这几样基本是在模板上设一次就不动的，摊开只会把保存键挤出屏幕。
  收起来之后整个弹窗 610px，iPhone 上一屏放得下，改时间完全不用滚。
  摘要那行（`更多设置（Work · 30–60′ · 陶土橙）`）让人不展开也知道里面是什么。
  新建时默认展开（要设分类），改已有的默认收起（十有八九只是改时间）。
- **光标默认落在哪一格看是哪一组**：计划落「开始」（改计划多半是挪起点），
  **实际落「结束」**（从 Actually 栏进来通常是「刚做完，补一下几点结束的」）。
  聚焦那一下「现在」浮层跟着弹出来，等于少点一次。

走完整个循环：长按实际块 → 点 OK → 点保存，三下，不滚动。

### 「现在」一键填

记实际时间时，那个时刻几乎总是「就是现在」，不该还要手打。点实际那一组的
开始或结束，格子下面浮出 **`现在 19:42` + OK**，一下填好，另外两格跟着算。

只对**实际**、而且只在**今天**出现 —— 别的日子的「现在」没有意义。

有个坑：`reconcile` 默认优先保住**时长**（手打计划时是对的，改开始等于整块平移），
但「现在」不一样 —— 它是真实发生的时刻，另一头如果也填了，那也是真的，
该保住的是另一头、重算时长。不然给一条 9:40–18:00 的记录把开始点成 19:42，
结束会被推到次日 04:02。区间要是颠倒了（现在比另一头还晚/还早），
就把另一头清掉让人重填，而不是存下 19:42–18:00 这种不可能的时间。

## 弹性任务：时长区间 + 排入

很多事「知道要多久，但不知道几点开始」——购物 30–60 分钟、晚餐 1 小时。
它们既不是固定日程，也不该只是一条没时长的待办。

- 待办可以写**时长区间**（最短 / 最长）。
- 点「排入 →」把它放到时间轴上：**自动找当天第一个装得下的空档**，
  按时长上限算。再排下一个自然接在后面，所以「下班后购物、晚餐、洗澡」
  点三下就依次排好了。
- **装不下也照排**（接在最后一个块后面，哪怕过了 24 点），只是标红。
  拒绝排入只会逼人跑去别处手动填时间；排上去、标红、自己拖，更有用。
- 「排入」和「开始」两个按钮紧跟在**时长**后面，不放在表格最右边 ——
  窄屏上这张表要横向滚到底才够得着，每次都得先划一下才能按。

## 周视图画哪一个：做完的画实际，没做的画计划

Week view 一条日程只画**一个**块，画哪一段按**条目状态**定
（`schedule.js` 的 `blockToShow`）：

| 这条 | 画什么 | 长什么样 |
|---|---|---|
| 做完了（有实际起止） | **实际** | 实线 |
| 正在计时 | 实际开始 → 现在 | 实线 |
| 还没做 / 还没到 | **计划** | **虚线 + 底色压淡** |
| 跳过了 | 计划 | 虚线 + 划掉 |
| 没有任何时间（待办） | 不画 | — |

**不按「今天之前 / 之后」切**。日期切法会在今天这一天出错：今天上午已经过完、
晚上还没发生，整天算「过去」的话晚上就一片空白，可你明明排了事。
按条目切，now 线左边自然是实际、右边是计划。

这条规则和 `place.js` 里 `busyIntervals`（算「今天还空着多少」的那个）
**是同一条**。共用一条规则是有意的：周视图讲的故事和加减法讲的故事永远一致，
只需要记一条，而不是两条。

顺带修好一个一直存在的空白：以前只画 `planned_*`，**「只记实际」的条目在周视图上
完全隐身** —— 临时去趟超市，那段是空的。现在它出现了。

一条目一个块、永远不画双份，所以信息更全但不会更乱。

### 压淡只压底色，不压整块透明度

「还没发生」要看着更淡，直觉做法是给整块加 `opacity`。**行不通** ——
三个要求会互相打架：淡得看得出来（实际↔计划底色 ΔE ≥ 3）要低透明度，
字要看得清（对比度 ≥ 4.5）要高透明度，块不能隐形（计划↔卡片底 ΔE ≥ 6）
也要高透明度。0.62 到 0.9 扫了一遍，**没有一个值三项全过**：

```
透明度 0.62  实际↔计划ΔE 3.4  计划↔卡片底ΔE 5.3  字对比度 2.8  ← 字看不清、快隐形
透明度 0.75  实际↔计划ΔE 2.3  计划↔卡片底ΔE 6.4  字对比度 3.8  ← 字看不清、和实际分不出
透明度 0.90  实际↔计划ΔE 0.9  计划↔卡片底ΔE 7.8  字对比度 5.6  ← 和实际分不出
```

根子在于整块透明会把**字一起拖下水**。把底色和墨色拆开就没这个矛盾了：
底色 `color-mix` 掺白掺到 45%，字和虚线边框**一点不动**。量出来：

```
实际↔计划 底色 ΔE  5.0–10.2   （最弱的是灰/Sleep，低彩度掺白掉得快）
字压计划底 对比度   9.5–10.2   （和原来一样，一点没退）
虚线边框压卡片底    2.3–2.8    （块的轮廓照样看得见）
```

块高只有十几像素、字才 0.6rem，字是绝对不能再淡的 —— 所以这条拆分是必须的，
不是偏好问题。

> 顺带删掉了两条旧 CSS：`.wt-block.status-done` 刷绿底（被块上的内联背景色盖掉，
> 从来没生效过）和 `.status-rescheduled` 画虚线（会和这套虚线打架 ——
> 做完的改期条目本该是实线）。

三个视图各答一个问题，谁都不越界：

- **Week view**：这周长什么样，哪天满哪天空
- **Day view**：计划 vs 实际，两栏并排看差值
- **统计**：长期差多少，哪一类老是超时

## 占用时段：做完的按实际算，没做的按计划算

「空着多少」和「排到哪」都得知道这一天哪些时段被占了。这件事**不能一刀切成
按实际算** —— 未来根本没有实际。今天下午三点的时候，晚上八点那件事只有计划、
没有实际，忽略计划等于假装晚上是空的。所以两者各管一段
（`place.js` 里的 `busyIntervals`）：

| 条目 | 占哪一段 |
|---|---|
| 做完了（有实际起止） | **实际**那一段 —— 计划那段就此让出来 |
| 正在做（in_progress） | 实际开始 → max(现在, 计划结束)，超时了就按已经拖到的时间算 |
| 跳过了 | 不占，让出来 |
| 还没做、有计划 | **计划**那一段，这是唯一的依据 |

好处最直观的是提前做完：计划 21:00 读书、结果下午三点就读完了，
那 21:00–22:00 现在真的是空的，加减法会多算出这一小时，「排入」也会把
下一件事放进去。反过来，晚上还没做的事照样占着位子，不会被排重。

两个函数共用同一份占用时段是有意的，不然会出现「说还剩两小时、
一点排入却塞不进去」这种自相矛盾。

## 块画成什么样，是算出来的

没有「是否已敲定」这类字段 —— 少一个字段就少一处可能和现实对不上的状态：

| 样子 | 什么时候 |
|---|---|
| 实心 | 起止都定死（min = max）且不和别的块冲突 |
| 半透明 + 虚线 | 时长还是个区间，没定死 |
| 半透明 + 红 | 和别的块撞了 |

手动拉过长短就等于你自己定了时长，区间收敛成定值，块随之变实心。

## 交互

块上的三个动作分开，互不误触：

| 动作 | 结果 |
|---|---|
| 拖**左边的竖条** | 挪时间 |
| 拖**底边** | 改时长（改完时长就定死了，块变实心） |
| **长按块** | 打开编辑，并且把**这一栏**对应的那组时间放在最上面 |
| **长按空白处** | 在那个时间加一条（见下） |
| 单击 | 选中（可以点好几个，然后一起拖） |
| 双击计划块 / 实际块 | 完成 / 撤销完成 |

### 双击不能让屏幕抖

双击一个块之前，浏览器会先发**两次 click**，也就是「选中 → 取消选中」。
而选中时弹出的操作条原本是普通元素，一出现就把下面所有内容顶下去
**107px**、一消失又弹回来 —— 双击于是变成两下抽搐。（这个数字是量出来的：
按帧采样 `document.body.scrollHeight`，看到 2089 → 2196 → 2089。）

两头一起堵：

- **操作条改成浮空**（`position: fixed`，固定在底部），不占文档流，
  页面高度怎么都不变。顺带它还永远在手边，不用往上滑找。
- **单击选中延后 220ms 生效**，第二下来了就把这次单击撤掉。
  220ms 几乎感觉不到，而双击是主操作（完成 / 撤销完成），
  选中只是拖动前的准备，慢一点无所谓。

浮条**不换行**：换行就摞成四层，手机上挡掉半个时间轴。放不下就把标题截断。

- 吸附到 5 分钟。拖动过程中实时判冲突 —— 松手之前就能看到变红。
- **Plan 和 Actually 两栏都能拖。**
- 手机上只有那两道窄条是拖动区（`touch-action: none`），块的其余部分
  照常点击和滚页面。整块都能拖的话，手指落在块上就滚不动 24 小时的时间轴了。
- **顺延**（默认开，时间轴右上角可关）：拖一个块，它之后的块跟着挪同样的量。
  一次拖动改的所有块算**一步撤销**。
  顺延**只对 Plan 生效** —— Actually 是「实际发生了什么」的记录，
  改一条不该顺手改掉后面几条已经发生的事。
- 拖动时的临时位置按 **(条目 id, 哪一栏)** 索引，不能只按 id：
  同一条日程在 Plan 和 Actually 各有一个块、id 相同，
  只按 id 匹配的话拖右边那个，左边的计划块会跟着一起动。
- 块放不下时**优先显示标题**，时间先省掉 —— 内容比时间重要。
- Actually 栏上方的「＋ 只记实际」：没排过计划、但确实做了的事，只填实际就行。
  这类条目只出现在 Actually 栏，不会跑到待办里。
- 小月历点某一天 = 直接进那天的 Day View。

## 撤销

**右下角固定的圆形按钮**（或 Ctrl/Cmd + Z）退回上一步，连着按可以一直退，最多 30 步。
按钮固定悬浮而不是放在顶栏 —— 页面很长，放顶栏每次都得往上滑才找得到。

实现方式是**每个写操作在动手之前先把「怎么撤回」记下来**（`usePlanner` 的 `act`），
而不是给整个状态做快照 —— 快照在多设备/多标签页下会把别人的改动一起冲掉。
唯一撤不干净的是「删除模板」：模板本身能原样回来，被连带删掉的打卡记录回不来。

## 删除是打墓碑，不是真删

模板每次打开 app 都会把「这一周还缺的」补生成出来，判据是
`(template_id, date)` 在不在。所以把行整个删掉，那个坑就空了 ——
**下次刷新它自己又长回来**。用户在 Day View 里删掉的任务刷新后重新出现，
就是这个。

改成打墓碑（`deleted_at`，`db/0009`）：坑还占着，生成器看得见、界面看不见。

- `listEntries` 过滤掉墓碑，所以界面、统计、汇总都当它不存在
- `listEntryKeys` **不**过滤 —— 它只给生成器用，就是要看见那个坑
- 撤销变成把 `deleted_at` 抹掉，比「连 id 一起重新插一行」干净得多
- 墓碑跟着 28 天的清理一起消失，不会越积越多

## 空白处长按 = 在这儿加一条

下班之后的活动本来就没计划：去了趟超市、临时出去玩。为了记一条，
原先得先点「＋ 只记实际」、打标题、再填两个时间 —— 比纸还慢。

**长按时间轴的空白处**（两栏都行，也可以点栏头的 `＋`），在按住的那个时间点
开一个小浮层：

- 顶上是**「几点开始」输入框**。默认值**不是手指按下去的位置** ——
  24 小时压在 1056px 里，一像素 1.4 分钟，手机上根本点不准。
  默认取**这一栏里最后一件在按压点之前结束的事的结束时间**，
  因为绝大多数时候下一件事就是接着上一件做的。旁边留了「现在」和
  「按的位置」两个按钮，想要原来的行为点一下就行。
- 中间是**今天还没安排的事**，点一下就放进去，时长用它自己的（`30–45′` 这种取上限）
- 下半截直接写一件新的，带一个时长输入框（默认 60 分钟）
- 加到 **Plan** = 打算做；加到 **Actually** = 做了（顺手记 `status = done`、完成度 100）
- 时间不准无所谓 —— 加上去之后拖块底边就能改，那本来就是这个 app 调时间的方式

几个实现上的取舍（`useEmptyPress.js`）：

- **不做成单击。** 24 小时的时间轴很长，手机上滚页面时手指落在时间轴上是常事，
  单击会一路误开。长按 520ms 才认，中途手一动（超过 8px）就取消。
- **不碰 `touch-action`，也不 `preventDefault`。** 空白处必须能照常滚页面 ——
  这和块上只有两道窄拖动条是同一个理由。用真实 touch 事件验过：
  在空白处上划页面照滚、浮层不开；按住不动 600ms 浮层才开。
- 按到 200ms 先画一道虚线加时间标签。这个手势本身完全看不见，
  按着没反应的话没人知道该继续按。
- 浮层开出来后 350ms 内不响应背景点击 —— 手指抬起那一下的 click 会落在背景上，
  不挡的话刚开就被自己关掉了。

## 统计的地基：分类 + 每日汇总

### 为什么要分类，而不是按标题统计

「地铁上班」「打车回家」「开车去客户那」是三个标题、同一类。
指望手打的标题一致本来就不成立，就算一致也解决不了这个。

分类挂在**模板**上，临时条目自己带一个。解析方式和颜色完全一样
（`categories.js` 的 `makeCategoryResolver`）：条目自己填了算「单独改过这一条」，
否则跟着模板走，**不往条目上复制**。

这条选择有个直接后果，而且是要的：把「读书」从学习改到休闲，历史统计整体跟着变。
个人工具改分类通常是因为想通了它本来就该属于那一类。

颜色也多了一层来源：**条目 → 模板 → 分类 → 默认色**。
「睡觉的颜色」和「睡觉这一类」不再是两套要手工对齐的东西了。

**分类只能停用不能删** —— 它是统计的维度，删掉会让那段历史无处可归。

### 明细留 28 天，汇总永久留

明细照旧 28 天就清（不回头看旧计划）。但清之前，每一天先被折成
`daily_rollup` 的几行：`(date, category_key, planned_minutes, actual_minutes, sessions)`。
一天 5–8 行、一年两千多行，**比明细还小四倍**。

为什么是汇总表而不是只存一个 EWMA 数字：min/max 是顺序统计量，EWMA 递推不出来；
n 周平均也不是 EWMA；而且 α 一旦选定就改不了了。有了汇总，
EWMA / n 周平均 / min / max / CSV 导出全部是读的时候现算的，α 想换随时换。

代价要说清楚：**明细删掉之后，那段时间的分类就改不动了。** 28 天之内改了分类，
下次打开重算就修好；更早的冻住。所以设置里有个「未分类」收纳箱，
按标题成堆归，趁早归完。

### syncRollups 的三个坑

`usePlanner` 挂载时按顺序做三件事：建默认分类 → **重算汇总** → **才清理明细**。
顺序反了的话，超过 28 天没打开 app，那段时间的统计就永远没了。

1. **重算而不是增量。** 整段覆盖是幂等的，漏跑错跑下次自动修好。
   增量要维护「统计到哪天了」的水位线，漏一次少一段、重一次多一段，
   而且出了问题根本发现不了。
2. **写的范围要盖住所有还存在的明细，不能只盖保留期。** 清理只在打开 app 时跑，
   六周没开就有 42 天的明细堆着，其中最老的两周正要被删。
   所以往回看 400 天（稳态下这个范围里其实只有 28 天的数据）。
3. **删的范围只能是保留期内。** 一个日期在汇总里有行、明细里却没有，
   在保留期内意味着「那天的条目被删光了」（该清），
   在保留期外意味着「明细早就被清理掉了」（绝对不能删，那是仅存的历史）。
   同一个现象，两种完全相反的含义，只能靠日期分开。
   —— 这条是写这块时最容易错的地方，第一版就错了，测出来才发现。

### 源头收敛：标题自动补全

快捷加一条的标题框，打两个字开始筛最近用过的标题（最多 5 条，按用得多 + 用得近排），
顺带把上次的时长和分类带过来。「去超市」第二次是点选而不是重打，
就长不出「去趟超市」「超市」这些同义异形的标题。

打一个字不筛 —— 候选太多，等于没筛。

## 统计页

顶栏「统计」进。数据只来自 `daily_rollup`，所以看多久的历史都行，
而**所有指标都是读的时候现算的** —— α 想换随时换。

- **统计起点**：默认下周一。刚开始用的那几天数据总是乱的，不值得算进去。
  存在 localStorage（换设备要再设一次）—— 它是「我从哪天开始认真记」的个人判断，
  为一个设置单开一张表不值当。
- 指标：执行天数、总时间、**日均 = 总时间 ÷ 执行天数**（不是除以日历天数）、
  日 min/max、占比、计划 vs 实际（差值 + 达成率）、n 周平均、EWMA。
- **min/max 只在做过的那些天里取**。不然只要有一天没做，min 永远是 0，这个数就废了。
- **达成率**对从来没排过计划的（临时事件）显示「—」，不显示 ∞。
- **「未记录」是一等公民**：单独一行、堆叠图里单独一段。不画它的话占比永远
  加不到 100%，而且「一天到底记下了多少」本身就是所有数字可信度的前提 ——
  记录率低于 50% 时页面会直接把这句话说出来。
- **堆叠柱的层序全窗口统一**（按各类总时长排，多的在下面）。一开始是每根柱子
  按自己那周的大小排，于是 Sleep 和 Work 谁在下面每周都在换 —— 柱子之间就没法
  互相比了，而堆叠图的意义正好在这。
- **整周没打开过 app 的那周不参与平均**。那是没记录，不是那周睡了 0 小时。
- EWMA 用第一个值起头，不用 0 —— 用 0 起头的话前几周会被一路拖低，
  看着像「最近在下滑」，其实是冷启动。

### 图表：手写 SVG

不引图表库。要的图就三种，加个库要多背一百多 KB，而且默认配色和这套莫兰迪
对不上，最后还是得一个个覆盖。颜色一律从分类来，图表和时间轴自动同色。

一条通用规矩：**SVG 里只放形状，文字一律用 HTML 放在外面。**
图要横向铺满容器只能用 `preserveAspectRatio="none"`，而那会把 viewBox
横向拉伸八九倍 —— 文字糊成一片、圆点变成椭圆。线宽用
`vector-effect="non-scaling-stroke"` 挡掉同样的问题。

趋势图的**纵轴不从 0 起**：每周睡 50 小时上下的曲线，从 0 起会贴着顶端拉成
一条直线，什么都看不出来。代价是波动被放大，所以图下面把纵轴范围明写出来。

### 导出

CSV **长表**（`日期, 周, 分类, 计划分钟, 实际分钟, 次数`），一行一天一类。
长表在 Google Sheets 里能直接做数据透视表，宽表不行。开头带 UTF-8 BOM，
不加的话中文在 Excel 里是乱码。

> 下载用的 `<a>` 必须先挂进 DOM 再 `click()`。游离的 `<a>` 在部分浏览器里
> 点了什么反应都没有 —— 这个是测出来的。

`habits_log` 和 `daily_rollup` 都**不参与清理**：前者本身就已经是汇总
（一天一个习惯一行、一年才两千行），删掉等于把打卡历史丢了。

## 装不装得下 / 计时

- **装不装得下**：To do 下面一行加减法 ——「剩下的时间还空着 4 小时 30 分；
  还没排的 3 件待办需要 2 小时 – 3 小时 15 分 — 装得下」，不够就变红写明差多少。
  纸质 planner 唯一做不到的就是这个加减法，我觉得它比替你排程更有用：
  知道差多少，人自己两秒就决定砍哪个。占用的时段按上面那张表算；
  已经做完的待办不再计入「还需要多少时间」。
- **计时**：出去玩、happy 这类事本来就猜不准时长，不如别猜。待办上点「▶ 开始」，
  顶部出现一条绿色横幅显示已经多久，Actually 栏里那个块跟着长到「现在」
  （每 30 秒重画），点「■ 结束」就落定。状态用的是 `status = 'in_progress'`，
  0001 的 check 约束里本来就有这个值。

## 配色

整体是**莫兰迪**：低饱和、掺灰的暖色，主色一味陶土橙（`--accent: #a95f33`）。

有一处不能照搬莫兰迪：**中间调上压白字对比度不够看**。所以状态色都给
「淡底 + 深字 + 同色描边」三件一套（`--ok-bg / --ok-ink / --ok`），
既是这个调子，也真的看得清 —— 打卡格、状态 pill、错误条全走这一套。
淡底还得够深，否则周视图那句「一眼看出哪天有任务没做」就不成立了。

- **颜色**：七个色（陶土橙 / 砖红 / 赭黄 / 鼠尾草 / 雾蓝 / 丁香 / 灰），
  不选就是陶土橙。时间轴的块、表格行前面的小圆点都跟着变。
  撞车时统一用红底 —— 那会儿警告比配色重要。
- 这七个是**算出来的，不是挑出来的**。第一版八个色两两之间的感知差异
  （CIEDE2000）最小只有 **3.3**，块底那一档基本分不出来 ——
  色相全挤在一起，而块底接近白、彩度低，色相差一压就没了。
  重做时把色相锁在 55/20/92/140/262/312 均匀铺开、明度也拉开，
  并且**砍掉青灰**（它就是鼠尾草的孪生兄弟，删掉后最小 ΔE 从 8.6 涨到 10.4）。
  现在块底最小 ΔE **10.4**、圆点 13.5、块底压深字对比度 ≥ 7.3。
  彩度上限卡在 17 / 27：放开能把 ΔE 拉更高，但那就成糖果色，不是这个调了。
  量色差的脚本在 `scripts/palette-check.mjs`。
- 颜色**不往条目上复制**，渲染时从模板取（`makeColorResolver`）。
  之前是生成条目时复制一份，于是改了模板颜色，已经生成的条目不会变 ——
  表现层的东西存成快照，迟早和现实对不上。
  条目自己填了颜色算「单独改过这一条」，优先于模板。
- 标题和「留」是**数据**，条目里存的就是副本，所以改模板时会
  **把今天及以后的条目一起改掉**（过去的不动，不改写历史）。
- **「留」**：待办前面的勾选框。默认不勾 —— 排进时间轴后它就归时间轴管，
  从待办列表里消失。勾上就两边都留着，列表仍然是「今天要做的全部事情」。
- **重复预设**：每天 / 工作日 / 周末一键选好。三餐这种每天重复的待办，
  建一次模板就行，不用每天手写，也不用点七下。
- 时间输入框的占位符是 `--:--` 而不是 `9:30` —— 后者看一眼分不清
  是自己填的还是提示。

## 几个约定

- **自动生成日程**：切到当前或未来的某一周时，按启用中的模板补齐这周的
  `schedule_entries`。`(template_id, date)` 上有唯一约束，重复生成是幂等的。
  过去的周不自动回填（避免凭空造历史）。
  订下周的计划就是切到下一周，模板会自动铺好，再手动调。
  「按模板补 N 条」这个按钮**只在真的还有东西可补时才出现**
  （刚建完模板、或者在看过去的周），平时不占地方。
- **habit 不进时间轴**：出现在 Habits 模块和 Day View 的打卡区，写入 `habits_log`。
- **改时间就是 reschedule**：原计划时间记进 `rescheduled_from`，状态置 `rescheduled`。
- **完成不删计划**：左栏计划块变淡，右栏出现实际块，保留计划 vs 实际的对比。
- **有没有计划时间决定去哪**：有时间的条目上时间轴，没时间的进 To do。
- **4 周保留**：App 挂载时清理一次 `schedule_entries` / `habits_log` 的过期数据
  （`RETENTION_DAYS = 28`），没有用 cron 或 Edge Function。
  `templates` / `weekly_focus` / `special_days` 是配置，永久保留。
  以后加统计功能时，统计结果单独落表，不受这个清理影响。

## PWA

可以直接「添加到主屏幕 / 安装」，装完是独立窗口，断网也能打开（数据仍需联网）。

- `public/manifest.webmanifest` — 名称、图标、独立窗口、主题色
- `public/sw.js` — 手写的 service worker，没引 vite-plugin-pwa
- `vite.config.js` 里的 `precacheServiceWorker` 插件在打包后把产物清单写进
  `dist/sw.js`。**这一步不能省**：service worker 要到页面 load 之后才注册，
  首次访问的那批 JS/CSS 不经过它，只靠运行时缓存的话装完当场断网就是白屏。
  清单的哈希同时当缓存版本号，资源一变旧缓存自动清掉。
- Supabase 的请求（跨域）一律不拦截不缓存 —— 缓存登录态和接口数据只会出怪问题。
- 查缓存用 `caches.match(..., { ignoreVary: true })`：静态服务器会回
  `Vary: Origin`，而预缓存请求不带 Origin、页面上 crossorigin 的请求带，
  不加这个参数缓存明明有也读不到。
